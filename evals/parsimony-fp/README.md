# Parsimony-verifier FP-rate harness (#436)

Empirical error-rate measurement for the **blind parsimony verifier**
(`packages/cli/src/loop/parsimony-verify.ts`) — the second, independent model
call whose `refuted` verdict **rejects children at enforce/full, the default**
(CLM-0177). The #415 consensus panel's convergent finding (#436): that verdict
is a nondeterministic model call being enforced on **without a measured error
rate**, and a _deterministic_ false refute (the verifier persistently misreads
a guard the diff genuinely satisfies) cannot be fixed by re-iteration — it
burns the full Kc child budget and terminates a legitimate child. This harness
produces the number that bounds that risk. [CLM-0196]

## What this is NOT

- **Not a gate.** `pnpm parsimony:fp` reports; it never fails the build on a
  measured rate (only on malformed/corpus-inconsistent ledger data). Acting on
  the number — e.g. revisiting the enforce-by-default ratification (#415) — is
  a **separate human-ratified decision**.
- **Not a benchmark of the assessor.** Only the verifier's confirm/refute over
  a _given_ claimed-pass set is measured. Applicability-under-claims
  (na-lying) are the verifier's documented blind spot (#435) and are **out of
  scope for scoring** here (two corpus cases record — but never score — that
  boundary).

## Layout

| file                             | role                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `corpus/*.json`                  | labeled cases: claimed-pass guard set, inline diff, per-guard ground truth, `labelProvenance` (HOW the truth is known), `scored` flag             |
| `run-fp-eval.mjs`                | operator-run runner — drives the REAL `verifyFloor` through the gate's own review-tier seam (real model calls; **not CI**), appends to the ledger |
| `results.jsonl`                  | the committed measurement ledger: one line per (case × rep)                                                                                       |
| `scripts/parsimony-fp-check.mjs` | deterministic, CI-safe scorer over the committed ledger (`pnpm parsimony:fp`)                                                                     |

## Corpus composition (19 cases)

- **4 real merged-PR excerpts** (extracted with `git show <sha> -- <file>`;
  exact excerpt boundaries documented per case in `source`):
  - `real-550-semver-guard` (#550, `bdaa79f`) — genuine input validation of a
    child-writable field (expected **confirmed**)
  - `real-571-document-audit` (#571, `154c357`) — genuine audit append on a
    side-effecting write (expected **confirmed**)
  - `real-571-document-claimed-validation` — the SAME #571 hunk claiming a
    guard it does not provide (expected **refuted**; probes claim-sensitivity)
  - `real-547-copy-claimed-accessibility` (#547, `a53c304`) — a no-UI plumbing
    diff claiming accessibility (expected **refuted**)
- **8 synthetic expected-confirm controls**, of which **3 are the
  confusable-phrasing false-refute risk class** the issue names
  (`synth-confusable-*`): the guard is genuinely provided but the prose
  invites a shallow misreading (e.g. "performs no sanitization" around a
  strict zod parse). These are the probes for the deterministic-false-refute
  class.
- **5 synthetic expected-refute over-claims** (`synth-log-only`,
  `synth-removed-bounds-check`, `synth-todo-audit`, `synth-swallow-catch`,
  `synth-comment-only-authz`) — measure the false-confirm side.
- **2 out-of-scope na-lying-adjacent cases (#435)** (`oos-*`, `scored: false`)
  — the claimed guard IS satisfied while an UNclaimed boundary is violated;
  recorded to observe scope-bleed, excluded from every headline rate.

### Labeling policy + exclusions

Labels are conservative: a case whose truth is arguable is **excluded**, since
a mislabeled corpus is worse than a small one. Excluded during construction:

- an `error_recovery` claim on the #547 copy diff — the cp→cpSync fallback
  appears mostly as moved/context lines, so "the DIFF provides recovery" is
  arguable either way;
- an `intent` claim on real diffs generally — "explicitly requested" is rarely
  objectively checkable from a diff excerpt alone (the one scored `intent`
  usage is confined to the unscored `oos-intent-with-unvalidated-boundary`).

Every case's `labelProvenance` states how its truth is known (merged-PR
behavior asserted by named tests / construction of the synthetic case).

## Generating measurements (live)

Reps require real model calls, so they are generated by hand, not in CI
(exactly like the vote-parity DPs):

```
pnpm build                                    # the runner imports the built dist
node evals/parsimony-fp/run-fp-eval.mjs       # --adapter claude --reps 3 by default
pnpm parsimony:fp                             # re-score the committed ledger
```

The runner binds the verifier exactly as the gate's composition root does with
no overlay overrides: `nodeRequirement('review')` → `resolveServed(adapter)` →
`buildNodeSeam` (tool-free reasoning posture) over `adapterInvoke` — and each
ledger row records the served model (`served`), so provenance never implies
more than ran. A malformed model emission is recorded as `parse_error`
(the gate would THROW there — parse errors are excluded from rates and
reported separately).

## Honest limits

- **Small corpus, weak bounds**: with ~10 expected-confirm cases × 3 reps, a
  measured 0% false-refute rate bounds the true rate only loosely (≈11% at
  95% confidence over 30 Bernoulli trials, and reps of the same case are not
  independent trials). The number is evidence, not proof.
- **Hand labels**: ground truth is human-assigned (provenance recorded per
  case); real-diff cases lean on merged, test-asserted behavior, synthetic
  cases on construction.
- **Nondeterminism handled by reps only** (default 3): per-case stability is
  reported so transient flake and deterministic disagreement — only the
  latter burns Kc — are distinguishable, but 3 reps is a coarse instrument.
- **One adapter/model per run** (recorded per row): rates are per-served-model,
  not universal.
- **Verdicts, not rationales**: `verifyFloor` returns only
  `{status, refutedChecks, cost}` — the emission's `reason` prose is discarded
  (as the gate does), so the ledger records THAT a case was refuted, never WHY.
  Reason capture for root-cause analysis is deferred to #574.

## First run (2026-07-03) and what it triggered

The first committed run (57 reps, `model:claude/sonnet@high`) measured a
**46.7% false-refute rate** (0% false-confirm; 3 persistent false-refute
cases). Weighing that number against the enforce-by-default posture
(#415/CLM-0177) is a human ratification decision tracked as #573 — this
harness only measures.
